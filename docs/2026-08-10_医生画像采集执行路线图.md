## 1. 路线图定位

本路线图面向管理员、Codex 和 Claude 三方协作执行，同时作为后续 Agent 快速接力的依据。

执行目标是：管理员不再逐个复制医生详情页链接，而是通过“Claude 读取入口台账选院并下发官网首页与医生目录 URL -> Codex 试采 -> Claude 审计 -> Codex 全量追加总底表 -> 生成 Obsidian 画像 -> 清理临时文件 -> 向 Claude 回报 -> Claude 选择下一家医院”的流程推进。

本路线图只允许使用医院官网等官方公开渠道，不使用第三方平台、不绕过登录或验证码、不采集患者评价和隐私信息。

## 2. 核心执行原则

1. 入口台账是医院采集入口的唯一执行依据。
2. 只有入口台账 `人工复核结果=确认可采集` 的医院可以进入任务；A级仅表示优先级，不能替代人工确认。
3. 每家医院正式追加前必须先试采。
4. 人工复核只复核试采样本，不要求复核全院所有医生。
5. 试采经 Claude 审计 `通过` / `有条件通过` 后，正式追加的数据默认视为可用数据，无需第二次业务审计。
6. 正式追加后，只有 `异常提示` 不为空的记录进入后续检查清单。
7. 试采质量差时，停止正式追加，记录该医院为未通过，等待人工处理或新增专用适配器。
8. 每家医院正式追加后立即生成或补充本院 Obsidian 画像。
9. 本院画像生成和索引核验完成后，Codex 回报 Claude 并停止；下一家医院由 Claude 选择。
10. 每轮采集和画像生成完成后清理临时试采文件，只保留总底表、总报告、必要 payload、画像报告和必要日志。

4. 通用模板医院不得跳过试采；专用适配器医院也应保留基本结果检查。
5. 试采质量差时，不要求管理员人工清洗大量错误数据，应停止正式追加并进入“待人工处理或新增专用适配器”状态。

## 6. 阶段 1：Claude 读取入口台账并选择医院

### 7.3 样本复核内容

3. 来源链接均来自医院官方域名或官方页面。
4. 没有批量采集到非医生内容。

## 11. 阶段 6：Obsidian 全量画像生成

### 11.1 当前状态

管理员要求每次正式追加总底表后立即开始 Obsidian 画像生成；画像完成后 Codex 向 Claude 回报并停止，Claude 再选择下一家医院。

当前 `generate_obsidian_profiles.py` 已具备统一总底表入口、缺失画像补充、报告修正覆盖和不覆盖人工精修画像等能力。后续单院追加后优先使用 `--generate-missing-only`，只补齐新追加医院缺失画像。

### 11.2 进入 Obsidian 阶段前必须完成

执行 Obsidian 画像前，需要先确认：

1. 统一总底表 CSV/XLSX 存在。
2. `generate_obsidian_profiles.py` 可运行。
3. 本轮正式追加已完成且更新报告已检查。
4. 使用 `--generate-missing-only` 时不覆盖已有人工精修画像。
5. 如管理员明确要求覆盖，才允许使用 `--admin-allow-overwrite`。

### 11.3 全量画像生成门禁

只有满足以下条件后，才进入画像生成：

1. 统一总底表存在。
2. 总底表中医院、姓名、来源链接字段基本完整。
3. 采集批次已完成或管理员明确允许中途生成。
4. 画像生成脚本已适配统一总底表。
5. 本轮医院正式追加已完成。

### 11.4 画像生成验收

验收标准：

1. 总底表中的医生均有对应 Markdown，除非姓名或来源链接缺失导致无法生成。
2. 医院目录结构清晰。
3. 医院索引页可打开。
4. 医生画像内容仅来自总底表字段。
5. 官网没有的信息保持空白。
6. 不生成疗效承诺、夸大表述或无来源亮点。

| 风险 | 等级 | 应对 |

| Obsidian 画像生成夸大宣传 | 高 | 画像只使用总底表字段；不得生成疗效承诺、排名、患者评价或无来源亮点 |
