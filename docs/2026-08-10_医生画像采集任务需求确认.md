# 2026-08-10 医生画像采集任务需求确认

## 1. 任务背景

本任务用于建设珠三角三甲医院医生 BD 画像库。目标不是直接生成对外宣传文案，而是先从医院官方公开渠道采集医生基础职业信息，结构化沉淀到统一底表，并在质量可控后转为 Obsidian 医生画像，供后续分析、筛选、BD 跟进和个人 IP 包装使用。

管理员要求流程尽量快、可重复、可由 Agent 按文档续接执行。管理员已授权在合规边界内升级脚本，减少逐个复制医生详情页链接的低效操作。具体执行分工、审计门禁和跨 Agent 交接规则以执行路线图为准。

管理员已确认本任务后续使用 GitHub 作为代码、文档和采集结果的版本协作渠道，目标仓库为 `https://github.com/nancywrayg57-jpg/doctor-data-collection.git`。本地 Codex 作为 developer，GitHub 账号为 `xtzhou247`，负责具体实现、采集执行和分支提交；Claude 作为 owner，GitHub 账号为 `nancywrayg57-jpg`，负责审计 Codex 的结果、指导下一步并输出 Codex 可自动读取的提示词。GitHub 具体流程和门禁以执行路线图为准。

## 2. 当前任务目标

1. 以珠三角地区明确三甲医院为第一阶段范围，优先按城市推进。
2. 基于医院官网等官方公开渠道，采集全院医生基础信息。
3. 对重点患者方向相关医生打标签，便于后续筛选和分析。
4. 将新增医生统一写入同一张总底表，避免为每家医院生成过多单独文件。
5. 对已通过复核的数据再生成正式 Obsidian 医生画像 Markdown。
6. 建立一套管理员可执行的半自动采集流程，后续可扩展到广东省及周边省份。

## 3. 第一阶段范围

### 3.1 地域范围

第一阶段仅包括珠三角官方范围内的三甲医院，按城市推进。

当前口径优先覆盖：

- 广州
- 深圳
- 东莞
- 珠海
- 中山
- 以及珠三角官方范围内其他城市

### 3.2 医院范围

只纳入医院等级字段明确为三甲或三级甲等的医院。

不纳入：

- 医院等级不明确的医院
- 仅疑似三甲但表格未明确标注的医院
- 非珠三角第一阶段范围医院
- 无法确认官方入口或无公开医生资料入口的医院

### 3.3 医生范围

采集口径为全院医生，但重点关注以下方向相关医生：

- 慢性病：高血压、糖尿病
- 肿瘤：淋巴癌、肺癌、肝癌、胃癌、肠癌等
- 生殖疾病：卵巢衰老、不孕症等
- 免疫功能低下
- 手术后恢复、康复
- 疑难重症、难治性疾病、复杂病例、罕见病等线索

## 4. 数据字段要求

统一总底表至少保留以下字段口径：

| 字段 | 要求 |
|---|---|
| 医院 | 必填，来自当前采集医院 |
| 姓名 | 必填，来自官方页面 |
| 科室 | 能采集则填写，无法判断则留空或标记复核 |
| 职称 | 能识别则填写；底表中只有“医师”的，按普通医生处理，职称写“医师” |
| 简介/擅长 | 官网有则摘录；官网没有则留空 |
| 重点关注范围 | 根据公开简介和擅长方向打标签，不强行推断 |
| 重点疾病标签 | 仅根据官方文本出现的疾病或方向标注 |
| 亮眼经历线索 | 只摘录官方公开资料中有证据的疑难重症、难治疾病、复杂病例、重要医疗经历等线索 |
| 来源链接 | 必须保留，可追溯到医院官方页面 |
| 采集日期 | 必须保留 |
| 异常提示 | 字段缺失、页面异常、疑似误识别等情况需标注 |
| 复核状态 | 默认待复核，人工确认后再标记已复核 |

缺失字段处理原则：

- 官网未展示的内容直接留空。
- 不通过猜测、搜索第三方或营销改写补齐字段。
- 简介较短的医生，无法采集足够信息时，相关字段留空即可。

## 5. 合规边界

### 5.1 允许来源

允许采集：

- 医院官网公开网页
- 医院官方发布的医生介绍页
- 医院官方科室或专家介绍页
- 医院官方公开小程序或公众号内容，但当前脚本主要适配网页，公众号和小程序更适合作为人工补充来源

### 5.2 禁止来源和行为

禁止：

- 使用第三方挂号平台、医生评价平台、非官方整理站
- 采集患者评价、排名、评论、问诊内容
- 采集私人手机号、私人微信、家庭住址、身份证号等个人隐私
- 绕过登录、验证码、反爬或权限限制
- 采集非公开接口或内部数据
- 对医疗能力作无证据包装
- 写出保证治愈、治愈率承诺、疗效绝对化表达

## 7. 当前脚本能力确认

当前脚本已经具备：

1. 自动读取官网入口台账。
2. 列出已确认可采集医院；A级只作为采集优先级。
3. 按指定医院从官网入口采集医生信息。
4. 对已接入专用适配器的医院进行稳定采集。
5. 对无专用适配器的医院使用通用官网模板试采。
6. 将正式新增医生追加到统一总底表。
7. 对重复医生进行跳过，减少重复写入。
8. 输出采集报告和异常提示。

当前脚本尚不等于“一键全自动跑完整个入口台账”。

当前限制：

1. 默认一次只处理一家医院。
2. 通用官网模板存在误识别风险，必须先小样本试采。
3. 通用模板全量追加前必须由 Claude 审计试采样本质量。
4. 公众号、小程序、需要交互的入口暂不适合脚本直接采集。
5. 不应让脚本在无人复核的情况下连续写入全部医院数据。

因此，当前推荐定位是：

> 官方渠道约束下的半自动批量采集工具。管理员负责在台账中确认入口；Claude 负责选择已确认医院、同时下发医院官网首页和医生目录 URL，并审计试采；Codex 负责指定医院的试采、字段标准化、去重、写入总底表和 Obsidian 画像生成。

## 9. 推荐执行流程

### 9.1 单家医院流程

1. 管理员在官网入口台账中确认医院入口。
2. Claude 读取台账和统一总底表，跳过未确认或已追加医院，选择目标医院并向 Codex 下发医院名称、医院官网首页和医生目录 URL。
3. Codex 对指定医院试采 10 位医生，不写入总底表，并提交 Claude 审计。
4. Claude 检查样本中的姓名、科室、职称、擅长、来源链接和异常提示，结论为 `通过`、`有条件通过` 或 `不通过`。
5. 试采通过后，Claude 下发完整执行指令；Codex 无需管理员二次确认，完成全量采集并追加统一总底表。
6. 如果样本质量不合格，不要求管理员人工清洗大量错误数据，应优先调整通用模板或增加专用适配器。
7. 正式追加后，Codex 检查总底表、CSV 和更新报告，生成本院 Obsidian 医生画像到 `医生画像仓库\01_试点医院`，核验索引并清理试采文件。
8. 完整执行结果无需再次业务审计；Codex 向 Claude 回报并停止，Claude 再选择下一家医院。

### 9.2 多医院推进流程

1. 只推进 `人工复核结果=确认可采集` 的医院；A级仅为优先级，未确认医院直接跳过。
2. 每家医院先试采 10 位医生。
3. 通过样本复核后再全量追加。
4. 每完成一家医院的追加和画像，Codex 回报并停止，由 Claude 重新选择下一家。
5. 批次稳定后，再考虑升级为“按城市自动试采队列”。

## 10. 质量验收标准

单家医院正式追加前，至少满足：

1. 样本医生姓名识别正确。
2. 来源链接均为医院官方域名。
3. 科室、职称、擅长字段没有大面积错位。
4. 新闻、公告、采购信息等非医生页面未被批量误识别为医生。
5. 异常提示可理解，便于管理员复核。
6. 官网没有的信息保持空白，没有补造。

统一总底表验收标准：

1. 新增医生写入同一张总底表。
2. 医院字段能区分不同医院。
3. 重复医生不会重复追加。
4. 来源链接和采集日期完整。
5. 待复核状态保留，方便后续人工处理。

Obsidian 画像验收标准：

1. 每位医生生成独立 Markdown。
2. 医生画像中保留医院、科室、职称、擅长、来源链接。
3. 亮眼经历只基于官方证据摘录。
4. 不生成夸大医疗效果或营销承诺。
5. `异常提示` 不为空、姓名明显不是医生姓名、或来源页明显为科室页/介绍页的记录，不应直接生成正式医生画像，应进入异常清单或待处理目录。
