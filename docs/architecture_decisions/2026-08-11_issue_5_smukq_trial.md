- 根因：导航剥离能力未作为所有长文本业务字段的统一前置门禁；测试只覆盖已知污染字段，没有覆盖 `亮眼经历线索 -> 画像可包装亮点/证据摘录` 的完整链路。
- 解决：新增 `extract_clean_highlights()`，在亮眼经历提取前剥离导航块及导航前页面列表；记录污染状态，清洗后无有效证据则留空，并写入 `已清洗/已清空` 透明提示。
- 预防：以后新增或修改任何正文派生字段时，必须同时覆盖 `原始正文 -> 字段抽取 -> 异常提示 -> 画像渲染` 四层测试；所有可能进入画像或对外引用栏位的长文本都必须执行导航检测，不能假定已清理其他字段即可复用原始正文。

### 2. 多入口医院在更新报告中只显示一个入口

- 阻塞：正式追加数据正确，但 `build_hospital_batches()` 使用 `first_nonempty()` 聚合，报告把 9 个入口压缩为单入口，无法证明覆盖范围。
- 解决：按医院保留全部唯一采集入口并增加多入口回归测试，不重跑网络采集、不重复追加数据。
- 预防：多入口适配器的验收必须同时核对 payload 入口列表、报告入口列表和各入口候选数；聚合报告不得用单值函数处理集合型字段。

### 3. XLSX 二进制资产无法用文本差分证明正确

- 阻塞：CSV/payload 的字段差分不能单独证明 XLSX 内容、工作表结构和样式未回归。
- 解决：修改前后均使用项目允许的 `@oai/artifact-tool` 导入并渲染六个工作表；后置检查将 XLSX 2088 行、23 列与总 payload 逐单元格对账，执行公式错误扫描，并用修改前基线识别既有显示问题。
- 预防：正式总表每次改动必须保留修改前视觉基线；交付前至少完成全表行列对账、关键范围检查、公式错误扫描和全部工作表视觉复核。预览中发现异常时先与基线比较，避免把既有数据问题误判为本轮回归。

### 4. 普通 Git HTTPS 推送在传输阶段卡住

- 阻塞：本机普通 `git push` 曾在 `git-remote-https` 阶段长期无响应，重复尝试会浪费时间并增加远端状态不确定性。
- 解决：只使用 GitHub Git Data API；推送前读取最新远端 HEAD，以其为 parent 创建提交，更新目标 ref 后对比本地/远端 tree SHA。
- 预防：本仓库遇到同类卡住时不重复普通 HTTPS 推送；先确认 `gh api user --jq .login` 为 `xtzhou247`，再核对远端 HEAD 未漂移，并以 tree SHA 一致作为成功证据。

### 5. 工作区存在用户/外部产生的 `.obsidian` 目录

- 阻塞：画像根目录出现未跟踪 `.obsidian/`，若使用宽泛的全目录暂存会把用户配置带入 PR。
- 解决：保留目录，不清理、不修改；提交时使用精确路径清单，并在提交前确认 `.obsidian/` 仍为未跟踪且未进入 staged diff。
- 预防：所有画像任务在暂存前必须检查未跟踪文件；不得使用覆盖整个画像根目录的宽泛暂存命令。

- 预防：进入等待态前必须完成提交、推送、tree SHA 核对和复审评论；进入等待态后不再做无关诊断或重复轮询命令，直到定时任务报告新审计或 PR 状态。

### 7. 验证运行时与标识符口径差异

- 阻塞：bundled Python 自带 `openpyxl`，但缺少采集器导入所需的 `requests` 和 `beautifulsoup4`；系统 `python.exe` 又只是 Microsoft Store 占位符。另一个验证器初版把单院 payload 的院内序号 1–95 误要求等于总表全局序号 1994 起。
- 解决：复用本 Issue 已保存的用户临时依赖目录，通过 `PYTHONPATH` 配合 bundled Python 复跑测试，不安装机器级依赖；跨资产对账以唯一 `来源链接` 为主键，比较全部业务字段，但明确排除作用域不同的 `序号`。
- 预防：后续先解析 Python 可执行文件与依赖实际路径，不依赖 Windows Store 占位命令；验证单院/总表镜像时必须先区分院内序号和全局序号等作用域字段，避免把验证器口径错误误报为数据缺陷。
