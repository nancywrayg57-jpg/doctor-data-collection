## 1. 目标与边界

TRIAL 先完成官网目录普查、349 个唯一 ArticleID 顺序详情核验、纯护理身份排除、10 位医生试采和本人职业照审计材料。owner 随后在 PR #48 明确审计“通过”并切换 `FULL_APPEND_AND_OBSIDIAN`；后续 FULL 结果与最终停止点见第 8 节起的追加记录。

固定边界：

1. 只使用 `gy120.net` 官网公开目录、数字 ArticleID 详情页和官方图片路径。
2. 详情只接受 `https://www.gy120.net/ArticleShow.asp?ArticleID=<数字>`，query 不得包含其他参数。
3. 旧 ASP 页面响应头没有 charset、meta 错标 UTF-8；响应体按 GB18030 严格解码，替换字符或高置信乱码标记触发写出前门禁。
4. 推荐区只作为角色证据，必须与科室树 ArticleID 重叠；正式身份按 ArticleID 去重，不按姓名猜测归并。
5. 只接受同域 `/files/<文件名>` 本人职业照；占位、空图、越界或其他旧路径只计数，不进入试采照片。
6. 图片请求只携带对应同域公开详情页 `Referer`。首次 HTTP 非 200 或 `Timeout` / `ConnectionError` / `ChunkedEncodingError` / `IncompleteRead` 后等待 1 秒，以同一 URL、同一 Referer、同一请求头只重试一次；不手工注入 Cookie、不绕过验证。连续两次失败按管理员裁决留空并标注。
7. 详情按顺序请求，不并发访问旧 IIS；FULL 在联网前硬熔断。

## 3. 实现决策

新增专用适配器 `gy120_asp_department_expert_photo`：

1. 精确识别唯一授权目录 URL，严格 GB18030 解码并校验医院/页面身份。
2. 只解析 `#a1 .index_list` 科室树；推荐区单独留痕，按数字 ArticleID 与科室树交叉对账。
3. 349 个详情只做顺序公开 GET；网络读取沿用有限三次详情请求，不使用并发。
4. 纯护理身份只依据详情“专业职称”排除，不按科室名称推断。
5. 试采从列表/详情姓名一致、身份非护理、严格本人职业照可得的候选中选 10 人；先保证首席专家、科室负责人、非推荐医生各至少 1 人，再最大化科室覆盖。
6. `.part2` 只提取官网出诊点标签；排班时段不进入正式字段。.part3 继续排除排名/患者片段、患者案例和导航噪声。
7. 图片保持官网原字节不压缩，记录 URL、详情 Referer、字节数、SHA-256、魔数、宽高、重试次数和两次失败结果。
8. 连续两次图片失败时清空照片字段并标注，同时清空重点标签、降为普通优先级；本次真实 TRIAL 未触发该降级。
9. FULL 模式在创建网络会话前硬熔断，必须等待 owner 在关联 PR 明确审计通过并切换 `FULL_APPEND_AND_OBSIDIAN`。

## 7. 阻塞、根因、解决与防复发

### 7.1 旧 IIS 并发读取发生响应体不完整

- 阻塞：前期 4 并发只读详情普查在约 100 个请求后发生 `ChunkedEncodingError` / `IncompleteRead`。
- 根因：旧 IIS 对并发批量响应不稳定，不适合作为本院采集策略。
- 解决：GY120 全目录改为顺序请求，真实 TRIAL 349/349 详情成功。
- 防复发：适配器不提供并发入口；报告固定记录请求方式，真实执行只允许一个进程。

### 7.2 科室分类估值与现场 DOM 不一致

- 阻塞：交接估值为“其他科室 29 / 医技 7”。
- 根因：估值未按四个 `index_list_*` 容器重新逐项统计。
- 解决：现场入口解析得到“其他科室 28 / 医技 8”，总科室仍为 57、关系仍为 349。
- 防复发：写出前门禁同时固定四类科室数、四类关系数、57 科室和 3 空科室。

### 7.3 护理人数预估错误导致首次写出前停止

- 阻塞：首次真实验证被门禁拦截，实际护理排除 2、医生候选 347，与未验证常量 4/345 不符。
- 根因：常量 4 来自专门护理科室的预估，不是 349 个详情“专业职称”全量核验结果。
- 解决：只按详情职称识别到 ArticleID 404、603 两个纯护理身份，将基线修正为 2；第二次且最终真实验证成功。
- 防复发：报告保留两条逐 ID 排除表；门禁要求护理详情集合与排除集合完全相等。若后续再次出现现场漂移，停止并重新审计，禁止按科室名猜测。

### 7.4 旧 `upsfile` 图片路径不在授权范围

- 阻塞：ArticleID 42 的图片 `upsfile/丁彩萍.jpg` 不符合预期 `/files/<文件名>` 路径。
- 根因：官网存在一条旧版图片目录遗留。
- 解决：TRIAL 先标为 `rejected`；owner 在 PR #48 明确扩展为同域、页面内本人头像 `upsfile/`，FULL 已纳入并完成照片字节闭环，未补第三方图片。
- 防复发：照片 URL 函数只接受同域 `/files/<安全文件名>` 与 owner 明确批准的 `/upsfile/<安全文件名>`；仍须由官网目录/详情页本人头像引用证明，其他路径继续拒绝。

### 7.5 第一次 FULL 写出前清洗门禁

- 阻塞：郑祥光的擅长尾部仍含“特需门诊时间：周四上午”；何智君官网正文含 `U+E06B` 私用区字符；旧排班正则又把论文作者“周四萍”误判成排班片段。该次运行在总底表写入前停止，三份受保护资产哈希保持第 5 节基线。
- 根因：GY120 旧页面的排班标签可出现在正文尾部；GB18030 正确解码后仍可能保留官网私用字形；无边界的“周四”规则不能区分星期与人名。
- 解决：增加 GY120 专用排班尾段清洗，只在明确标签/时段结构成立时移除；私用区字符在适配器边界删除但不猜字；异常行取消标签提权。修正后专项与全量测试通过。
- 防复发：FULL 写出前同时扫描正式字段中的排班标签/时段、全部基础字段中的私用区字符和异常行提权；测试固定“周四萍”不被误删。

### 7.6 第二次 FULL 详情漂移门禁

- 阻塞：一个详情在 `fetch_gy120_html` 的三次有限请求后仍失败，旧 FULL 门禁把 `detail_error_count=0` 与照片可得 347 写成静态常量，导致候选 346 并停止写表；受保护总底表仍未变化。
- 根因：Issue 已固化“详情失败保守成行”，但 FULL validator 仍沿用 TRIAL 的零失败与固定照片常量，采集器也先过滤了失败详情，契约不一致。
- 解决：保留目录姓名、科室和官方详情来源；失败详情按逐 ID 留痕保守成行、照片留空、异常标注、取消标签提权。TRIAL 继续固定零详情失败；FULL 改为动态核对失败 ID、`detail_errors`、照片可得/留空四数。新增合成详情失败回归测试。
- 防复发：FULL 门禁不再把瞬时详情成功数写死，但必须维持 349 个目录 ID、2 个已审计护理 ID、347 个合规候选和失败详情逐 ID 对账；未知失败不得静默丢行。
